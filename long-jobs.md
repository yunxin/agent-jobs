# Long jobs: what the agent follows

This is for the agent. It says how a long job is launched and reported,
and what a verb doc and a script for one must contain. A person asks for
the pair once per project; the doc is theirs after that.

## Launching a job

- Run it under the wrapper, detached, so the command returns at once:

  ```bash
  nohup <ai>/agent-jobs/bin/agent-job <command> > /dev/null 2>&1 &
  ```

  `<ai>` is the `ai/` folder this clone is in. If the shell tool ends every
  process when the command returns, use the tool's own background option
  for this line instead.

- Then end the turn. Do not poll, sleep, or tail the log. The report
  arrives on its own once the job finishes and you have been idle since.

- Act on the report when it arrives. The default report is the command
  and its exit code. A command says something better by writing one line
  to `$AGENT_JOB_MSG_FILE`, which the wrapper provides; the scripts below
  do that.

## Writing a verb doc

A verb doc is a markdown file named for what it does, `run-ci.md`, in the
folder the person made in `ai/`. It is written once, for them to read and
settle, and it is followed after that, never edited by the agent. It says:

1. The launch line, with the script's path.
2. That the turn ends, with no polling.
3. What the report looks like and what to do with each outcome.
4. That the scripts beside it cover the usual runs, that a run they do not
   cover gets a new script beside them, and that this file is not edited.

The one for CI:

```markdown
# Run CI

1. Start it detached, so the command returns at once:

   nohup <ai>/agent-jobs/bin/agent-job <ai>/ci/run-ci.sh > /dev/null 2>&1 &

   If your shell tool ends every process when the command returns, use the
   tool's own background option for this line instead.

2. Say that CI is running, and end your turn. Do not poll, sleep, or tail
   the log: the report arrives on its own once the run ends and you have
   been idle since.

3. Act on the report. `run-ci: PASS log=<path>` needs no more than a word
   to the user. `run-ci: FAIL rc=<n> log=<path>`: read the log at that
   path, fix what it shows, and run CI again the same way.

4. The scripts beside this file cover the usual runs. For a run they do
   not cover, write another script beside them. Do not edit this file.
```

## Writing a script

A script for a long job does three things: sends the run's output to a log,
prints one verdict line for a caller, and writes one line to
`$AGENT_JOB_MSG_FILE` when the wrapper provides it, so the report names the
outcome and where the details are. One `emit()` does the last two at every
exit path. The one for CI, with the project's command in place of
`make check`:

```bash
#!/usr/bin/env bash
# run-ci.sh — run CI as a self-reporting job. Arguments replace the
# default command. CI_LOG chooses the log file.
set -uo pipefail

if [ $# -gt 0 ]; then cmd=("$@"); else cmd=(make check); fi
CI_LOG="${CI_LOG:-$(mktemp "${TMPDIR:-/tmp}/run-ci.XXXXXX")}"

# One line for the wrapper's report, when a wrapper is running this.
report() {
  [ -n "${AGENT_JOB_MSG_FILE:-}" ] && printf '%s\n' "$1" > "$AGENT_JOB_MSG_FILE"
  return 0
}

# The one exit: the verdict line for a caller, the same words for the agent.
emit() {
  local verdict="$1" code="$2" detail="${3:-}"
  printf 'VERDICT=%s LOG=%s\n' "$verdict" "$CI_LOG"
  report "run-ci: $verdict${detail:+ $detail} log=$CI_LOG"
  exit "$code"
}

printf '[%s] run-ci: %s\n' "$(date -u +%FT%TZ)" "${cmd[*]}" > "$CI_LOG"
"${cmd[@]}" >> "$CI_LOG" 2>&1
rc=$?
if [ "$rc" -eq 0 ]; then emit PASS 0; else emit FAIL 10 "rc=$rc"; fi
```

A job that watches something elsewhere, a remote build for instance, has
the same shape with a poll in the middle and more verdicts: green, a real
failure, an infrastructure failure, a timeout. Each one is a line for
`emit()`, with the run's URL in the message.

## Adding scripts

The scripts in the folder are the usual runs. For a run they do not cover,
a subset of tests or a different target, write another script beside them
in the same shape, and keep it. Do not write a script for one run and
discard it, and do not add or edit a verb doc: the docs are the person's.
